## 核心工程贡献

章节位于“项目要解决的问题”之后，使用“问题、实现、结果”组织以下内容：

### OCR 分区与统一结构

- 将图纸内容组织为标题栏、技术要求、全局文本和布局信息。
- 使用固定 JSON 契约约束 Qwen OCR 输出。
- 将 MinerU Markdown、表格和 content list 映射到相同数据结构。
- 两个 OCR 后端复用数据库、检索、展示和导出链路。

### OCR 可靠性优化

- PDF 分页渲染并限制处理页数和输入规模。
- 单页失败不阻断其他页面；全部页面失败时不写入空成功记录。
- 兼容 Markdown 代码围栏和非标准 JSON。
- 从 MinerU 结果中提取技术要求编号段落和页面下部标题栏表格。
- 保存原始结构化结果用于追溯。

### MechVL 提示词与上下文引导

- 组合图纸预览、标题栏、技术要求、全局 OCR 和用户问题。
- 明确要求模型依据不足时说明，不得编造尺寸、材料、公差或标准条款。
- 使用 OCR 上下文补偿图像缩放后可能丢失的细小标注。
- 对模型答案执行轻量清理以适配工作台展示。

### 单卡模型调度

- MinerU 与 MechVL 互斥驻留。
- 任务忙碌期间拒绝切换。
- 启动失败、超时和异常退出时回收目标进程。
- 暴露切换阶段、已用时间和基于历史记录的预计剩余时间。

### 模块化架构

- 将原单文件应用拆分为配置、路由、服务、仓储和模型服务。
- HTTP、业务逻辑、数据库和模型调用可以独立测试。
- OCR 或视觉模型替换不要求同步修改主要路由和数据库层。

## 前后版本对比

以模块化重构提交 `5cb4bc0` 的父版本为旧版基线，以当前 PR 分支为新版。使用相同 Python 环境和同一台机器测量：

| 指标 | 测量方法 |
| --- | --- |
| 最大 Python 文件行数 | 统计两个版本受 Git 管理的 `.py` 文件 |
| 业务模块数量 | 统计应用业务 `.py` 模块，不含虚拟环境和生成文件 |
| 应用导入时间 | 新进程重复导入应用，报告中位数 |
| 核心只读路由延迟 | 相同临时数据库下重复请求，报告中位数和 P95 |
| 自动化测试数量 | 两个版本可发现并执行的测试数量 |
| 可自动验证故障场景 | 按测试用例和明确断言统计，不按代码分支猜测 |
| OCR 后端和互斥保护 | 根据可执行代码与测试判断有无 |

应用导入和路由延迟只衡量代码架构开销，不与 MinerU/Qwen/MechVL 推理耗时混合。若新版速度持平或回退，README 如实报告；模块化收益主要从最大文件规模、职责隔离、测试和故障保护解释。

稳定性不使用没有长期运行记录支撑的百分比。使用测试数量、故障场景数量、忙碌保护、超时处理和真实模型互斥验证作为证据。
